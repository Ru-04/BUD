# API contracts (health, chat, preferences, memory, transcribe and speak implemented)

All endpoints under `/api` use JSON except audio upload/output. Visitor identity is a client-generated opaque token sent as the `X-Owner-Token` header (not a body field, not `/api/sessions` — see Gate 3 implementation notes below); the server only ever stores its SHA-256 hash. This is a **local-dev visitor-isolation mechanism**, not a settled production access policy — see `docs/scope.md` open decision 2 before public deployment. Error envelope: `{ "error": { "code": "...", "message": "..." } }`. Validate length, IDs, content type, rate and upload size. Never accept preference values outside 0–100.

| Method | Route | Auth | Request | Response |
| --- | --- | --- | --- | --- |
| GET | `/health` | — | — | `{ "status": "ok" }` |
| POST | `/api/chat` | `X-Owner-Token` optional | `{ "session_id": "uuid", "message": "text", "history": [] }` (`history` optional) | `{ "reply": "text", "mode": "LISTEN", "sensitivity": "normal", "memory_candidate": null }` |
| POST | `/api/transcribe` | none | multipart `audio` field, ≤10MB, one of `audio/webm`/`audio/ogg`/`audio/wav`/`audio/x-wav`/`audio/mp4`/`audio/x-m4a`/`audio/mpeg` | `{ "transcript": "text", "language": "English" }` (Whisper's own detected-language label, may be uncertain) |
| GET | `/api/preferences` | `X-Owner-Token` required | — | four 0–100 values |
| PUT | `/api/preferences` | `X-Owner-Token` required | `{ "warmth": 70, "humour": 40, "sarcasm": 15, "directness": 60 }` (all 4 required) | saved values |
| POST | `/api/memory-candidates/{id}/approve` | `X-Owner-Token` required | — | `{ "memory_id": "uuid", "approved": true }` |
| POST | `/api/memory-candidates/{id}/reject` | `X-Owner-Token` required | — | `{ "rejected": true }` |
| GET | `/api/memories` | `X-Owner-Token` required | — | approved items only, `[{ "id", "content", "category", "approved_at" }]` |
| DELETE | `/api/memories/{id}` | `X-Owner-Token` required | — | 204 |
| POST | `/api/speak` | none | `{ "text": "..." }`, 1-4000 chars | `audio/wav` binary |

`/api/transcribe` returns text, then the frontend calls `/api/chat`; no second conversation pipeline. Transcription errors leave typed chat available. `memory_candidate` shape, if present: `{ "id": "uuid", "content": "...", "category": "communication_preference" }`; no persistence to approved memories until the approve endpoint succeeds, and a candidate not approved within 24h expires and can no longer be approved. Do not return private internals or free-form analyzer reasoning to the browser.

## Gate 3 implementation notes

`/api/sessions` as a standalone endpoint was **not built**; the frontend still mints its own `session_id` client-side (`crypto.randomUUID()`), and the backend lazily registers the `sessions` row (with the caller's hashed owner token) the first time that `session_id` is used in `/api/chat`. A client that reuses a `session_id` under a *different* `X-Owner-Token` gets `403 SESSION_OWNER_MISMATCH` — this is the concrete two-visitor isolation guarantee, verified by both unit tests and a live cross-token check.

`/api/chat`'s `X-Owner-Token` is optional: without it, chat behaves exactly as in Gate 2 (ephemeral, no persistence, `memory_candidate` always null). With it: both turns are persisted to `messages`; that owner's saved `preferences` and approved `memories` are loaded and folded into the generation prompt; and, only when this turn's sensitivity is `normal`, a memory-candidate extractor call may propose at most one candidate (never for `sensitive`/`urgent` turns, and a failed/slow extractor — bounded to 8s — never breaks the chat reply itself). The frontend always sends this header now (a token generated once via `crypto.randomUUID()` and kept in `localStorage`), so in practice every browser session gets full persistence.

`message` is trimmed and must contain 1-4000 characters. Optional `history` defaults to `[]`, and contains at most 12 turns (6 complete user/assistant pairs) with roles `user` and `assistant`, 1-4000 characters each and 24000 characters total. Unknown fields, invalid UUIDs, system roles and incomplete/out-of-order pairs are rejected. Client-supplied `history` is still what's sent to Groq for conversational context (unchanged from Gate 2); the newly-persisted `messages` table is a durable record, not (yet) the read path for context. Client history is untrusted; it grants no access to other conversations. The UI retains conversation state only in the current tab; reload/clear removes it, and only the bounded recent history is sent to Groq. This does not make a claim about Groq's retention policies.

Errors use the documented envelope. Validation: 422 `INVALID_REQUEST`; oversize audio: 413 `INVALID_REQUEST`; configuration: 503 `NOT_CONFIGURED`; upstream authentication: 503 `PROVIDER_AUTH`; quota: 429 `PROVIDER_RATE_LIMIT`; timeout: 504 `PROVIDER_TIMEOUT`; unavailable/rejected/invalid upstream responses: 502; session reused by a different visitor: 403 `SESSION_OWNER_MISMATCH`; unknown/expired/not-owned memory candidate or memory: 404 `NOT_FOUND`. Provider bodies, keys and analyzer internals are not returned. Total chat deadline is 55 seconds; individual provider requests have a 20-second timeout; `/api/transcribe` also has a 20-second provider timeout. The UI has a 60-second deadline and preserves unsent text after failures. Requests use JSON (multipart for `/api/transcribe`) and local CORS permits GET/POST/PUT/DELETE plus `Content-Type` and `X-Owner-Token`.

The analyzer receives one schema retry; two malformed outputs or confidence below 0.6 produce a deterministic LISTEN clarification, not a fabricated provider reply. Provider transport failures return errors instead. Local contextual safety cues run before any provider call and cannot be downgraded by the analyzer. An urgent finding returns a fixed supportive response without reply generation. Sensitive findings suppress humour/sarcasm/flirting in the highest-priority generation instructions, in code as well as in the prompt (see `docs/prompts.md`). These instructions constrain generation but do not establish a universal guarantee about model behavior. Pattern coverage and live model quality require ongoing evaluation; this is a local prototype, not a crisis service. Public access/rate limiting and a settled visitor-identity policy still require the deployment decision gate.

## Gate 4 implementation notes

`/api/transcribe` sends the uploaded audio straight through to Groq Whisper (`whisper-large-v3`) in memory over HTTPS; it is never written to disk on the backend, matching `docs/scope.md`'s "keep raw recording only during transcription" boundary. It supplies Groq's real (docs-verified) `prompt` parameter with a short neutral context sentence expecting Hindi/English code-switching and Indian-accented English, to reduce Whisper hallucination on short/ambiguous audio -- a style hint, never a vocabulary list, and never used to "correct" the transcript after the fact. `language` is deliberately left unset so Hinglish isn't forced into one language; `temperature` is left at Groq's own recommended default (`0`). It does not require `X-Owner-Token` — the resulting transcript is just placed in the browser's message composer for the user to review/edit, then sent through the normal (optionally token-bearing) `/api/chat` call; there is no separate voice conversation pipeline. Live-verified end-to-end with genuine synthesized English speech (Windows SAPI, not a text fixture) through the real Groq API: exact transcript returned, `language: "English"` detected correctly, and the transcript successfully carried through to `/api/chat` for a normal reply. Hinglish/Hindi live transcription accuracy has **not** been verified in this session (no Hindi text-to-speech voice available locally to generate a synthetic sample) — needs the user's own voice via the browser mic. A React.StrictMode double-mount race in the browser recording component was found and fixed (a stale, orphaned `MediaRecorder` kept capturing audio uncontrolled after "pause"), which may also have been corrupting audio quality generally.

`/api/speak` (user-directed addition, engine confirmed with the user: Groq's `canopylabs/orpheus-v1-english`, not the originally-recorded Piper stretch-goal choice, since Orpheus is hosted, already available on the account, and specifically known for expressive human-like speech) synthesizes the given text and returns one playable `audio/wav` clip. Orpheus's documented input limit is 200 characters per call and only `wav` is supported as `response_format`; the backend splits longer text into <=200-char chunks at sentence boundaries (falling back to word boundaries for a single long sentence) and stitches the resulting WAV clips into one file via Python's `wave` module, so the response always matches the single-clip contract regardless of reply length. Does not require `X-Owner-Token`. **This model requires one-time terms acceptance** in the Groq console (a manual, login-gated step only the account owner can do) before the API will serve it; until then the backend returns `503 MODEL_TERMS_REQUIRED` with a message pointing at `console.groq.com/playground`. TTS audio has not yet been live-verified pending that acceptance.
